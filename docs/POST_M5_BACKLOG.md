# Post-M5 backlog: findings to track after Milestone 5

This file lists problems and improvements found while reviewing the code, the design, and the security of RiskForge that are **not** fixed yet. Work on them after Milestone 5 (portfolio hardening), or earlier when the ticket named in the last column starts. Fixed findings are not listed here; they are in the review tables of `docs/M3_NOTES.md` and `SYSTEM_DESIGN.md` section 17.3.

The findings of the Milestone 4 review (RF-017 to RF-021) are tracked separately in [`POST_M5_BACKLOG_M4.md`](POST_M5_BACKLOG_M4.md).

How to use it: one row is one trackable item. Change **Status** when work starts (`Open`, `In progress`, `Done: <commit or PR>`). Add new findings at the end of the right table with the next free id. Keep each row factual: what was observed, where, and what to do.

Severity: **High** can expose data or give a wrong decision in production. **Medium** weakens security or reliability under load or misuse. **Low** is maintainability, ergonomics, or a documented limit.

Origin: `M3 review` means found in the Milestone 3 validation (RF-011 to RF-016); other values name the earlier review.

## Security

| Id | Severity | Finding | Evidence | Suggested work | Status | Related ticket |
|---|---|---|---|---|---|---|
| SEC-01 | High | The decision tables store the applicant's financial input in clear text (`decision.runs.input_snapshot`, `outcome`, `rule_traces.inputs`). There is no retention period, no masking, and no encryption at rest. The append-only triggers refuse `UPDATE` and `DELETE`, so a data subject's record cannot be erased without bypassing them. `TRUNCATE` is not blocked for the table owner. | `database/migrations/20261127000001_create_decision_tables.go`; `SYSTEM_DESIGN.md` 7.4 asks for minimization, retention, and secure erasure before real personal data. Demo data is synthetic, so this is not exploitable today. | Decide the data classification of each dictionary variable. Add retention and a controlled erasure path (for example a `decision.purge` function owned by a separate role, audited). Consider column encryption or storing only the fields needed for replay. Restrict `TRUNCATE` by privileges. | Open | RF-022, RF-026 |
| SEC-02 | High | No rate limit on `POST /decisions/evaluate` (or on login). `SYSTEM_DESIGN.md` 15.1 asks for rate limits and payload limits on the public decision endpoint. Only the 64 KiB body limit and the 3 second timeout exist. | The only mention of a limiter is the Goravel scaffold facade `app/facades/rate_limiter.go`; no route or middleware uses it. | Add a per-client limiter in front of the decision routes (and a stricter one on login). Return `429` with `Retry-After` and document it in OpenAPI. | Open | RF-023 |
| SEC-03 | Medium | Machine callers are ordinary users. Any user with the `API_CONSUMER` role may evaluate **any** product, idempotency keys are scoped to the user id, and a consumer authenticates with a user password and a bearer token. | `decision.requests.client_id` references `identity.users`; `docs/M3_NOTES.md` (RF-015 table); OpenAPI says "Any `API_CONSUMER` may evaluate any product". | Introduce `api_clients` (hashed API key or client credentials, allowed products, quota). Keep the per-client idempotency scope. | Open | M4/M5, `SYSTEM_DESIGN.md` 7.2 |
| SEC-04 | Medium | Body withholding in `activity.log` is a deny list (`withheldBodyPrefixes` in `app/platform/logging/redact.go`). It protects `/api/v1/decisions...` only. The policy simulator (RF-017) will also take applicant data, and any later route that does will leak it into the log in dev and test (the release image already sets `LOG_HTTP_BODIES=false`). | `LOG_HTTP_BODIES` defaults to `true` in `config/logging.go`. The M3 review found full applicant bodies in `storage/logs/activity.log` before the fix. | Add the simulator route to the list when RF-017 lands, or invert the rule: log bodies only for an allow list of routes (auth, catalog, dictionary, policy configuration). Add a test that fails when a route that takes `applicant` is not withheld. | Mitigated for the simulator (RF-017: every `/api/v1/policy-versions/.../simulate` path is withheld, tested in `withheld_test.go` and `TestTheActivityLogNeverContainsTheSimulatedApplicant`); the rule is still a deny list | RF-023 (allow list) |
| SEC-05 | Medium | A duplicate request with the same `Idempotency-Key` waits on the unique index of `decision.requests` until the first request commits or the 3 second timeout cancels it. Each waiter holds a database connection and a goroutine. A client can park many connections with many duplicates of a slow request. Behavior at the timeout boundary was not tested. | `docs/M3_NOTES.md` "Deferred from the review". | Set `lock_timeout` for the claim statement and answer a retriable `409`/`425`-style error; test the boundary. Combine with SEC-02. | Open | RF-023 |
| SEC-06 | Low | Idempotency keys never expire. `decision.requests` grows with every decision and the keyspace of one client is unbounded. | Append-only triggers; no retention (`SYSTEM_DESIGN.md` 7.3). | Define key retention (for example 24 hours for replay, then archive) together with SEC-01. | Open | RF-022 |
| SEC-07 | Low | Reading a decision (`GET /decisions/{id}`) and evaluating one are not audit events; failures are only in `error.log`. | No audit module yet; `docs/M3_NOTES.md` RF-015 table. | Write audit events (who, when, action, entity, version, result) once RF-022 exists. | Open | RF-022 |
| SEC-08 | Low | Dependency vulnerability scan never ran: `govulncheck` could not reach `vuln.go.dev` from the development environment. | `SYSTEM_DESIGN.md` 17.1. | Run `govulncheck` and a container image scan in CI. | Open | RF-025 |
| SEC-09 | Low | Bounds that analysts define for dictionary variables (`DecimalBound`) and scorecard bins (`BinBound`) still allow a fraction of any length (`[0-9]+`). Applicant input is now limited to 32 fraction digits. Only users with write permission can send them, and the body limit bounds the size. | `decimalPattern` in `app/modules/dictionary/domain/variable.go`; OpenAPI `DecimalBound`, `BinBound`. | Limit the fraction to `MaxScale` digits in the bounds and in the OpenAPI patterns in one contract change. | Open | RF-025 |

## Reliability and performance

| Id | Severity | Finding | Evidence | Suggested work | Status | Related ticket |
|---|---|---|---|---|---|---|
| REL-01 | Medium | A policy version that cannot be compiled is remembered as an error (`ErrPolicyConfiguration`) until the process restarts or the 64 entry LRU evicts it. Fixing the code that made the snapshot unreadable needs a restart. | `docs/M3_NOTES.md` RF-016 table; `policy_cache.go`. | Give cached errors a short time to live (for example 1 minute), or expose a cache flush for operators. | Open | RF-023 |
| REL-02 | Low | Cache statistics (`PolicyResolver.CacheStats()`) have no endpoint or metric, so hit rate is invisible in production. | RF-016 notes. | Export hits, misses, loads, waits, and entries as metrics. | Open | RF-023 |
| REL-03 | Low | One decision runs three reads before the evaluation: product lookup, binding join, and (on a miss) the snapshot. The product lookup and binding join could be one query. | `PolicyService.ActiveReference`. | Measure with real latency first (RF-024), then merge if worth it. | Open | RF-024 |
| REL-04 | Low | `BuildFacts` sorts and copies the dictionary on every evaluation (about 130 µs per decision including everything else). | RF-016 notes. | Precompute per compiled policy if RF-024 shows it matters. | Open | RF-024 |
| REL-05 | Low | Only completed decisions are stored. A technical failure (`EVALUATION_ERROR`, `POLICY_CONFIGURATION_ERROR`, `500`) leaves no row, so incident review depends on `error.log`. | `SYSTEM_DESIGN.md` 10.5 lists `FAILED` as a processing state; the code keeps it only in the response. | Record failed attempts as audit events (not as decisions) with request id and policy version. | Open | RF-022 |
| REL-06 | Low | The cache is per process. With several instances each one has its own cache; the immutable key makes them consistent but each pays its own first load. | Design 10.6 accepts this for the MVP. | Revisit with multi-instance deployment; consider warming the cache at start. | Open | after M5 |

## Design and architecture

| Id | Severity | Finding | Evidence | Suggested work | Status | Related ticket |
|---|---|---|---|---|---|---|
| ARC-01 | Medium | Policy publication for real does not exist yet. The active policy of a product is created only by `DemoActivePolicySeeder` (local and testing). The seeder is the single bypass of the approval workflow and must disappear (or stay dev-only behind the same guard) when publish exists. | `SYSTEM_DESIGN.md` 17 ("production evaluation endpoint tidak boleh memiliki bypass"); `database/seeders/demo_active_policy_seeder.go`. | Implement approval and publish (RF-018 to RF-020); add a test that no non-seeder code path writes `active_policy_bindings` except publish. | Open | RF-018..RF-020 |
| ARC-02 | Medium | A decision matrix row has no reason code, so a matrix `REJECT` or `REFER` returns an empty `reason_codes`. A caller cannot tell why a score was rejected. | `SYSTEM_DESIGN.md` 10.8 ("keputusan terbuka"). | Decide: add an optional `reason_code` to matrix rows (schema, validation, snapshot format 3, OpenAPI) or document a fixed code per outcome. | Open | M4 |
| ARC-03 | Low | `SYSTEM_DESIGN.md` 13.3 shows a response example that differs from the implementation (`policy_version` is an object, `bin` is a label, no `execution_ms`). The deviation is documented in 10.9 but the example is the old one. | Sections 10.9 and 13.3. | Replace the example in 13.3 with a real response, or mark it conceptual. | Open | docs |
| ARC-04 | Low | Resolver and cache tests live in `database/seeders` because they reuse the demo policy fixture. | RF-016 notes. | Move the fixture to a shared test-support package. | Open | RF-025 |
| ARC-05 | Low | The module `decision` reads policies through `PolicyService` (a use case of another module) via a small interface. This is acceptable for a modular monolith, but the interface `ActivePolicyService` is defined in `decision/infrastructure`, not in `decision/application`. | `policy_resolver.go`. | Keep as is until a second consumer exists; then move the port to the application layer. | Open | after M5 |
| ARC-06 | Low | `request_hash` is computed from the parsed JSON (numbers as `float64`), so `1` and `1.0` hash the same and an integer above 2^53 would lose digits in the hash. Money is a string and integers above 2^53 are refused, so no accepted request is affected. | RF-015 notes. | Hash the raw canonical bytes if a numeric field with larger values is ever accepted. | Open | after M5 |

## Testing and tooling

| Id | Severity | Finding | Evidence | Suggested work | Status | Related ticket |
|---|---|---|---|---|---|---|
| TST-01 | Medium | The Postman smoke run cannot exercise the decision happy path: it uses the read-only auditor, so `evaluate` answers `403`. Happy and unhappy decision flows are covered by Go HTTP tests and by the manual script in `docs/VERIFICATION.md`, not by the collection. | `scripts/smoke-postman.sh`. | Add a second Newman run as `demo_loan_application` with a generated `Idempotency-Key` that checks `200`, the replay header, `409`, `422`, and `404`. | Open | RF-025 |
| TST-02 | Low | `gofmt -l` inside the container lists almost every file on a Windows checkout, because the working tree has CRLF line endings (`core.autocrlf`, `.gitattributes` has `* text=auto`) while gofmt wants LF. A real formatting error is hidden in that noise. | Seen during the M3 validation; the index holds LF. | Add `*.go text eol=lf` to `.gitattributes` and run `gofmt -l` in CI on a clean checkout. | Open | RF-025 |
| TST-03 | Low | The full race test run takes about 7.5 minutes (`tests/feature` alone is 440 seconds) because suites share one database and run in sequence. | M3 validation timing. | Split the suites per schema or per database, or run packages in parallel in CI. | Open | RF-025 |
| TST-04 | Low | A test database that was used by the live API (bcrypt cost 12) makes `go test` fail with `408` on login. This is documented in `AGENT_RUNBOOK.md` but easy to hit when one `rf-test-*` project is used for both a live run and the test suite. | Seen during the M3 validation. | Make the test harness detect a cost-12 hash and fail with the runbook hint, or give live runs and test runs separate projects in the runbook examples. | Open | docs |
| TST-05 | Low | Concurrency tests of duplicate requests are repeated eight times, not under a stress profile. No test covers a waiter at the 3 second timeout. | RF-015 notes. | Add a timeout-boundary test together with SEC-05. | Open | RF-023 |
